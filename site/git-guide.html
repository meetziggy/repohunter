Why version control exists

Ever had a folder like project_final, project_final_v2, project_final_REALLY_final? That's version control done by hand — badly. It loses history, breaks collaboration, and there's no "undo" when something goes wrong.

Version control fixes this. It records every meaningful change to your files as a snapshot you can name, revisit, undo, and share. You get a full timeline of your project, the ability to jump back to any point, and a safe way for multiple people (or you + an AI agent) to work on the same code without clobbering each other.

What Git actually is

Git is the tool that does version control — by far the most popular one. It runs on your computer and quietly tracks your project's history. GitHub (and GitLab, Codeberg, and others) are websites that host your Git projects online so you can back them up, share them, and collaborate. Git ≠ GitHub: Git is the engine; GitHub is one place to park it.

The 4 ideas to grok

TermPlain English
Repository (repo)Your project folder, but with a memory. Once it's a repo, Git tracks everything in it.
CommitA saved snapshot with a message ("added login page"). Like a checkpoint in a video game — you can always return to it.
BranchA parallel copy where you try things without touching the main version. Break stuff safely, then merge it back when it works.
RemoteThe online copy (e.g., on GitHub). You push your commits up to it and pull others' changes down.

Your first repository

1

Install & introduce yourself

Get Git from git-scm.com (macOS/Linux often have it already; type git --version to check). Then tell it who you are — this stamps your commits:

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
2

Turn a folder into a repo

# from inside your project folder
git init

That's it — Git is now watching this folder.

3

Make your first commit

git add .            # stage everything (mark it to be saved)
git commit -m "First commit"   # save the snapshot with a message

You just created your first checkpoint. git status shows what's changed; git log shows your history.

⚠️ Never commit secrets. API keys, passwords, .env files — once committed and pushed, they live in history forever, even if you delete them later. Add a .gitignore file listing things to skip (like .env, node_modules/). When in doubt, don't commit it.

Push it to the cloud

Now back it up and share it. Create an empty repo on your host (see Where to host it), then connect and push:

git remote add origin https://github.com/you/your-repo.git
git branch -M main
git push -u origin main

Your code is now safely online. Refresh the page and you'll see it.

The everyday loop

99% of Git is these few commands, over and over:

git pull            # get the latest (if collaborating)
# ...do your work, edit files...
git add .           # stage your changes
git commit -m "what you changed"
git push            # send it up
💡 Commit often, in small chunks, with clear messages. "Fixed login bug" beats "stuff." Future-you (and anyone reading) will thank you.

Branches & pull requests

When you want to try something risky — or work with others — make a branch:

git checkout -b my-feature   # create + switch to a new branch
# ...work, commit...
git push -u origin my-feature

Then on GitHub you open a Pull Request (PR) — a proposal to merge your branch into main. Others (or you) review it, then merge. This is how nearly all collaboration and AI-assisted work happens: changes land as reviewable PRs, not surprise edits to main.

Cloning & reusing code

To grab a copy of someone's public project:

git clone https://github.com/owner/repo.git

Now you have the whole thing locally. But before you build on it — check the license and credit the author (that's the whole reuse-first ethos, and there's a right way to do it). And before you adopt anything, it's worth asking: is this repo actually worth reusing, for my project? That's literally what RepoHunter is for.

Alternatives to Git

Git won, but it's not the only option:

ToolWhy you'd look at it
Jujutsu (jj)A newer, friendlier front-end that works with Git repos — many find it easier to reason about.
Mercurial (hg)A cleaner, simpler design than Git; used by a few big projects.
FossilAll-in-one (version control + bug tracker + wiki) in a single file. Great for solo/small.
Subversion (SVN)The older centralized model; still around in some enterprises.

For 99% of people starting today: learn Git. It's what the world uses, and everything else can wait.

The cheat sheet

git init                    # start tracking this folder
git status                  # what's changed?
git add .                   # stage all changes
git commit -m "message"     # save a snapshot
git log --oneline           # see history
git clone URL               # copy a repo
git pull                    # get latest from remote
git push                    # send your commits up
git checkout -b name        # new branch
git checkout main           # switch back to main
git merge name              # merge a branch in
git diff                    # see exact changes
git restore file            # undo unstaged changes to a file
